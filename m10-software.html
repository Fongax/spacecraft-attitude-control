MODULE 10

Software engineering and embedded code

The same control laws, written as code that has to run on a small flight computer: one interface for every controller, a loop that never misses its deadline, numbers that never overflow, data that is never half-written, and tests that can catch what a single plot cannot.

    One specification, several programs

    The project wrote its attitude controller more than once. The main program is a MATLAB simulation whose core functions sit underneath two user interfaces, a modern one and a legacy one for older installations Project. Beside it sit an optional Python validation mirror, which reads the CSV files the simulation writes and checks them, and an optional embedded-style C++ controller stub Project. This site's JavaScript engine is a fourth program built from the same specification Site default.

    Several programs for one specification sounds wasteful, but each answers a different question. The simulation asks does the design work? The mirror asks did we compute what we think we computed? It is a sanity check by a second route, the habit the Design of Machine Elements notes close every worked example with. The stub asks could this run on a flight computer? The Intelligent Systems notes give the vocabulary: the control laws plus the mode table are one agent function; the simulation, the C++ stub and this site's engine are agent programs that realise it, so comparing their outputs tests that they agree on that one function; the Python mirror instead re-checks one program's outputs.

    The danger in several programs is drift. The inertia, the ±0.003 N m limit and the thresholds 6 and 0.5 deg/s, 2 s, 4° and 8 s Project appear in every one of them. The Software Engineering and Architecture notes put it precisely: DRY is about knowledge, not characters, and the test is "will these always change together?" Writing the dynamics in three languages is legitimate duplication of code; the constants, equations and conventions must stay single-sourced. On this site every page reads them from one object, ADCS.params, and never types them again.

    Reading files, writing functions and loops, handling exceptions and using NumPy arrays are the skills the mirror needs, and they are typical content of an introductory programming-for-engineers subject Typical content. If the controller ever moved to separate hardware for a hardware-in-the-loop test, the interface between simulator and controller should be written schema-first, with the schema as the interface document, as the Networking notes describe for RPC. The messages are tiny:

    \[ \underbrace{7\times 8\ \text{B}}_{q,\ \omega}=56\ \text{B per state},\qquad \underbrace{3\times 8\ \text{B}}_{\tau}=24\ \text{B per torque command} \]

    The same notes measured that compressing a single small record made it larger, so per-step packets should be sent as they are Derived.

    Controller interface and mode manager

    The project has three control laws, detumble, PID and LQR, and a mode machine that decides which one runs. In C++ that is one abstract base class and three derived classes. The sketch below was written fresh for this site Site default; it shows the shape, not the project's own stub.

    enum class Mode : std::uint8_t { Nominal, SafeDetumble, SafeHold };

class AttitudeController {
public:
    virtual ~AttitudeController() = default;           // safe delete through a base pointer
    virtual Vec3 torque(const State& s, const Quat& qRef, double dt) = 0;
    virtual void reset() {}                             // PID clears its integral here
protected:
    static double sat(double u) noexcept {              // one limit for every law (REQ-S2)
        return u > kTauMax ? kTauMax : (u < -kTauMax ? -kTauMax : u);
    }
    static constexpr double kTauMax = 0.003;            // N m per axis
};

class DetumbleController final : public AttitudeController {
public:  Vec3 torque(const State& s, const Quat& qRef, double dt) override;   // -Kd w
};
class PidController final : public AttitudeController {
public:  Vec3 torque(const State& s, const Quat& qRef, double dt) override;
         void reset() override;                                               // zero the integral
private: Vec3 integral_{};
};
class LqrController final : public AttitudeController {
public:  Vec3 torque(const State& s, const Quat& qRef, double dt) override;   // -K [2 qe_v; w]
private: double K_[3][6];                                                     // stored gains
};

class ModeManager {
public:
    Status update(double rateDeg, double errDeg, bool fault) noexcept;   // status code, never throws
    Mode   mode() const noexcept { return mode_; }
private:
    Mode mode_ = Mode::Nominal;
    std::uint16_t faultTicks_ = 0, belowTicks_ = 0, dwellTicks_ = 0;    // integer timers
};

    Three details matter. The saturation helper is protected, so every derived law calls the same limit and a future controller cannot "forget" REQ-S2; inheritance, protected members and exceptions are all in the Object-Oriented Programming (C++) notes. The mode and its timers are private to ModeManager behind one update(), so no outside code can force a forbidden SAFE_DETUMBLE → NOMINAL jump; the forbidden transitions become impossible by construction. And every override is marked override: if a signature drifts, say const State& becomes State, the compiler reports an error instead of silently creating a new function that is never called while the base behaviour runs. override, final and virtual destructors are typical content of a short C++ inheritance exercise Typical content.

    The mode manager itself should be table-driven, not polymorphic. The Software Engineering and Architecture notes say plainly that "a state machine dispatching on a status field is not polymorphism". A transition table of (from, to, guard) rows is reviewable data, and the absence of a NOMINAL → SAFE_HOLD row is the proof that the transition cannot happen:

    The mode table as data Project
    FromToGuard
    NOMINALSAFE_DETUMBLE|ω| > 6 deg/s, or fault active ≥ 0.5 s
    SAFE_DETUMBLESAFE_HOLD|ω| < 0.5 deg/s held for 2 s

    Where do errors go? In ground tools such as a batch runner, the UI or a CSV loader, a non-physical input (dt ≤ 0, a NaN rate, a fault window that ends before it starts) should throw an exception, as the C++ notes teach with throw, try and catch. Flight code is different: many embedded coding standards restrict exceptions because stack unwinding has unpredictable timing, so the flight-style stub should be noexcept, return status codes and fall back to safe values. This site's engine behaves like a ground tool: give it an impossible scenario and ADCS.sim.run throws a RangeError, which every widget catches and shows inline.

    The real-time loop

    On a flight computer the controller is a loop driven by a timer interrupt: read the sensors, decide the mode, compute the control law, saturate, write the torque command, wait for the next tick. The Electromechanics notes describe exactly this digital scan loop and its rule of thumb: the scan delay acts like dead time, so scan at least ten times faster than the fastest dynamics being controlled.

    How fast is fast enough here? The LQR closed loop has natural frequencies of 0.89 to 1.12 rad/s Derived, a bandwidth of about 0.14 to 0.18 Hz:

    \[ f_{bw}\approx\frac{\omega_n}{2\pi}\approx 0.18\ \text{Hz}\quad\Rightarrow\quad f_s\ \ge\ 10\,f_{bw}\approx 2\ \text{Hz},\qquad \phi_{ZOH}\approx\frac{\omega T}{2} \]

    Sampling 10 to 30 times the bandwidth, and the phase lag \(\omega T/2\) that a zero-order hold adds, are typical content of a control-systems subject Typical content. At 10 Hz (\(T = 0.1\) s) the lag at 1 rad/s is 0.05 rad, about 2.9° Derived. So 10 to 100 Hz loops are comfortable; this site runs its controller every 0.01 s Site default. The fast inner current loop of the wheel motor is another matter, with a time constant near 0.1 ms, and lives in the motor driver.

    The control task shares the processor with an estimator, telemetry and logging, so something has to decide who runs. The Database Infrastructure and OS Internals notes measured the convoy effect: without preemption, short jobs queue behind a long one. Only preemptive scheduling, here fixed-priority, guarantees that a long telemetry dump never delays the control step. With priorities set by period (shorter period, higher priority), the classic sufficient test is the rate-monotonic bound Extension:

    \[ U=\sum_{i=1}^{n}\frac{C_i}{T_i}\ \le\ n\left(2^{1/n}-1\right)=0.780\ (n=3),\ \ 0.757\ (n=4),\ \ \to\ln 2\approx0.693 \]

    Here \(C_i\) is each task's worst-case execution time and \(T_i\) its period. WCET must assume cold caches: the same notes measured memory access up to 4.31 times slower after another task evicted the cache. Control data should flow through a capacity-one "latest value" mailbox, because a queue of stale measurements is pure phase lag; commands and events need a bounded FIFO, whose blocking is visible backpressure rather than silent memory growth.

    No heap, no recursion, fixed buffers

    A hard deadline is a worst-case promise, and memory management is where worst cases hide. The Systems Programming and Memory notes measured a malloc and free pair at about 2.2 ns when the allocator recycles a block, but 50.9 ns or more when the heap has to grow, with fragmentation and a NULL return as new failure modes. A garbage collector is worse: its pause grows with the live set, 191 ms at a million objects, longer than the whole 100 ms budget of a 10 Hz loop. And the most dangerous bug of all is silent: a leak exits 0. The notes held 509 MB with no error at all. A few bytes leaked per control cycle pass every short test and exhaust memory days into a mission, ending in a watchdog reset and an unplanned safe-mode entry.

    So flight code allocates everything once, at start-up: the 10-element state \([q,\ \omega,\ \textstyle\int e]\), the four RK4 stage vectors, the gain table, and a ring buffer for telemetry that overwrites its oldest sample. The Computing Algorithms notes add the decisive argument against growable arrays: a doubling array has amortised O(1) appends, but the occasional append costs O(n) and a heap allocation, and amortised is the wrong guarantee when every single tick has a deadline. Safety-critical coding rules in the "Power of Ten" style say the same: no dynamic allocation after initialisation, no recursion (so the worst-case stack depth can be computed), and a fixed upper bound on every loop.

    \[ M_{ring}=N\,s,\qquad N=\Big\lceil\frac{T_{keep}}{\Delta t}\Big\rceil:\qquad 60\ \text{s at 10 Hz}\ \Rightarrow\ 600\times 41\ \text{B}\approx 24.6\ \text{kB} \]

    A 41-byte telemetry sample (q, ω and τ as 32-bit floats plus a mode byte) kept for 60 s Derived from Illustrative choices.

    This site's engine follows the same pattern where it matters for speed: ADCS.sim.run allocates its log arrays (\(n = T/\Delta t + 1\) rows) once before the loop starts, and the loop only fills them. Sanitizers belong in the test build, not the flight build, and they need care: the same notes measured AddressSanitizer at about 2.8 times the cost of each memory access, and found that at -O1 the optimiser had already deleted three of five planted bugs before it could see them.

    The rule reaches beyond control laws. An on-board planner needs memory-bounded search: the Intelligent Systems notes measured IDA* using 277 times less peak memory than A* for 1.076 times the work. A small neural network is surprisingly flight-friendly for the same reason; its forward pass is a fixed sequence of multiplies, and an example 6-16-3 network has exactly \((6+1)\cdot16+(16+1)\cdot3=163\) weights Illustrative, a footprint known before launch.

    Units, word sizes and fixed point

    Units. The project states its thresholds in deg/s and integrates in rad/s Project, so one forgotten conversion is a factor of 57.3. The Design of Machine Elements notes warn about the same class of trap again and again (rev/min against rad/s is a factor of 9.55, N m against N mm a factor of 1000) and answer it with unit-suffixed names and a sanity check by a second route.

    Fixed point. A small processor may send the torque command as a 16-bit two's-complement number scaled to the limit (Q15):

    \[ \Delta\tau=\frac{0.003\ \text{N m}}{2^{15}-1}=9.2\times10^{-8}\ \text{N m}\ \approx\ \frac{2\times10^{-5}\ \text{N m}}{218} \]

    so quantisation is about 200 times finer than the disturbance bound and negligible Derived. The arithmetic must saturate on overflow rather than wrap: a wrapped command turns the largest positive torque into the largest negative one. Number formats, two's complement and saturating arithmetic are typical content of a computer-architecture subject Typical content.

    Word sizes. The 8 s dwell is 80 ticks at 10 Hz, which fits a uint8_t (at most 255), but 400 ticks at 50 Hz, which needs a uint16_t; this site counts 800 ticks at 100 Hz and logs its counters as 16-bit integers Derived. Counting integer ticks is exact; adding 0.01 s to a float 800 times gives 7.99999999999987, so a t += dt timer fires one step late, at 801 steps Derived. A free-running 32-bit millisecond counter wraps after

    \[ 2^{32}\ \text{ms}\approx 4.29\times10^{9}\ \text{ms}=49.7\ \text{days},\qquad \text{elapsed}=(\text{now}-\text{start})\bmod 2^{32} \]

    and the Data Structures notes show why unsigned now − start stays correct across one wrap (modular arithmetic) while signed overflow is undefined behaviour in C and C++.

    Memory layout. MATLAB stores matrices column by column; C and C++ read a flat array row by row. Port the 3 × 6 LQR gain matrix as a flat array without transposing and attitude and rate gains land on the wrong axes. Nothing crashes. The same notes file this with their many "plausible wrong answer, no error" findings, and the widget shows what it does to a real run.

    Shared state: the torn quaternion

    In a typical flight split, an estimator task writes the attitude \(q\) and other tasks (telemetry, the mode supervisor) read it. Four numbers cannot be written in one instruction. If the reader runs between the writer's first and last component, it gets a torn read: part old attitude, part new.

    \[ q_{read}=\big[q_0^{new},\ q_1^{new},\ q_2^{old},\ q_3^{old}\big],\qquad \lVert q_{read}\rVert\neq1 \]

    A non-unit quaternion is not an attitude at all, and every rotation built from it is skewed. The Systems Programming and Memory notes give the recipe for any race: it needs shared mutable state, a writer and a non-atomic operation, all at once, and every fix removes one of them. A double buffer writes into a hidden copy and publishes it with one atomic pointer swap. A sequence lock lets the reader detect a write in progress (an odd or changed counter) and retry. A message queue hands over immutable snapshots. A mutex works too, but makes the reader wait.

    Testing cannot prove a race away. The notes ran the same racy code twice and lost 60,000 of 80,000 updates in one form and none in another, so a passing test proves nothing; stress tests with injected delays, thread sanitizers or model checking of the hand-off are needed. The Data Structures notes' lesson "individual operations are safe; sequences are not" applies equally to a fault word updated with fault_word |= bit from both an interrupt and the control task.

    Locks bring their own failures. If the supervisor takes the mode lock and then the actuator lock while the controller takes them in the other order, the notes' measurement applies: inconsistent lock ordering deadlocked 39 of 40 trials, consistent ordering none. One global order (state, then mode, then actuator) fixes it. Priority inversion is the bridge to scheduling Extension: a low-priority task holds a mutex the high-priority task needs while medium-priority tasks preempt the holder. A well-known Mars lander suffered repeated resets from exactly this until priority inheritance was switched on for the mutex.

    Testing

    A plot of one good run tests one case. Code needs tests that check rules over many inputs. Property tests state a law that must hold for every input and then try hundreds of random ones:

    \[ \lVert q\otimes p\rVert=1,\qquad C^{\top}C=I,\ \det C=+1,\qquad C(q)=C(-q),\qquad |\mathrm{sat}(u)|\le\tau_{max},\qquad \mathrm{sat}(\mathrm{sat}(u))=\mathrm{sat}(u) \]

    Small, single-purpose functions with clear contracts, such as "quat_to_dcm of the identity is I" or "a DCM is orthonormal", and unit tests for them are typical content of a programming-principles subject Typical content. Writing the last two laws as machine-checked contracts, in the same lemma style as "reversing a list twice gives the list", is typical content of a logic and automated-reasoning subject Typical content. The widget below runs these laws against the site's real helpers and against deliberately broken copies, and shows an uncomfortable truth: some tests cannot see some bugs.

    Regression baselines. Store "golden" CSV outputs from a reviewed run with a fixed seed, and compare every new run with a tolerance (for example a relative 10⁻⁹), never with bit-equality. Tagging each automated test with the requirement it verifies, so the traceability table can be generated from the test suite, is typical content of a software-projects subject Typical content.

    Cross-implementation checks. To compare two implementations, such as the simulation and this site's engine, compare the mode sequences first. Run-length encode each mode log into tokens, then compute their edit distance by dynamic programming, as the Algorithms notes do with Levenshtein distance: 0 means identical mode histories, and otherwise the traceback points at the divergence, often a one-sample-late transition from a float comparison. Numeric channels are compared with tolerances. Two defensive habits from the Python Programming for Search and Constraint Satisfaction notes carry straight over: never mutate a collection while iterating over it, and make state canonical before comparing it (for a quaternion, flip the sign so the scalar part is not negative).

    Inputs from people need tests too: range checks, NaN rejection and "fault window start before end" in the UI, and hashes of result files so published evidence can be checked, are typical content of a security-standards subject Typical content.

    Reproducibility and tool independence

    A result that only runs on one machine is not evidence. The project hit this in its third iteration: the LQR design may need an optional toolbox. The decision was to save the fallback gain matrix in the parameter file, so the project runs without it; the lesson recorded was "tool independence improves reproducibility" Project. The risk register adds two more mitigations: fix the random seed for Monte Carlo, and write all outputs to CSV Project.

    The same thinking runs through the rest of the project. The shared simulation, plotting and animation code avoids newer-only language features, ships its own degree–radian helpers for older installations, and falls back from MPEG-4 to Motion JPEG video when the newer format is not available Project. Pinning library versions so the Python mirror runs anywhere is the same dependency-management decision, and is typical content of a software-projects subject Typical content. Good tabular data design (one row per trial, explicit units, a recorded seed) is typical content of an information-systems subject Typical content.

    The Data Structures notes add two finer points. Write tables with a deterministic key and column order, so two runs produce byte-identical CSV files that can be diffed. And identify each run by a hash of its canonical parameters (J, limits, gains, Q and R, seed, dt), so a stale result is detectable. The birthday bound says how many bits that hash needs:

    \[ n_{50\%}\approx1.18\sqrt{2^{b}}:\qquad b=32\ \Rightarrow\ n\approx7.7\times10^{4}\ \text{runs} \]

    so a 32-bit run ID has an even chance of a collision after about 77,000 runs, and 64 bits or more is the safe choice Derived.

    This site applies the same rules. Every number comes from one parameter object; every scenario can be written into a link (the address after # encodes the scenario, so the simulator replays it exactly); the Monte Carlo generator is seeded and bit-exact with the reference implementation used to check this site; and every run can be downloaded as CSV from the simulator Site default.

      In short: the control laws are the easy part of flight software. The hard parts are structural: one interface and a table-driven mode manager, a preemptive loop with a computed worst case, no allocation or recursion after start-up, units and word sizes chosen on purpose, shared data that can never be read half-written, and several kinds of test, because each kind is blind to some bugs.
