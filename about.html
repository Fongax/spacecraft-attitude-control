What the project is

The original project is a MATLAB-based nonlinear simulation of a small rigid spacecraft's attitude control. It models reaction wheels with a torque limit and a three-mode safe-mode logic, compares a PID controller with an LQR controller, and produces its verification outputs automatically: response plots, a test matrix, a requirements trace and a Monte Carlo campaign. The results can be watched as a 3D attitude animation, and an interactive interface lets the user change the initial attitude and body rates, the controller, the run duration, safe mode and a fault window, then save the run as a CSV file. An optional Python validation helper re-checks the CSV outputs that the MATLAB workflow writes, and an embedded-style C++ stub sketches the controller as flight code. Project

Its main modelling assumptions, as the project states them:

  • the spacecraft is a rigid body with a diagonal, constant inertia matrix;
  • attitude is propagated with scalar-first quaternions;
  • the reaction wheels are commanded body torques with per-axis saturation;
  • the disturbance torque is bounded and constant within each run;
  • the LQR is designed on a small-angle linearisation near the target, while the simulation uses the full nonlinear quaternion dynamics;
  • the 3D animation is a representative picture of the attitude, not a detailed CAD model.

In scope and out of scope

In the original project Project

  • Rigid-body dynamics with the gyroscopic coupling term, and quaternion kinematics.
  • Reaction-wheel torque limits on each axis.
  • A quaternion-error PID and an LQR for nominal pointing, rate damping for detumbling and a low-gain hold.
  • The NOMINAL, SAFE_DETUMBLE and SAFE_HOLD mode machine with fault injection.
  • Five requirements, six tests and a 60-trial Monte Carlo campaign.
  • The 3D animation, the interactive interface, the Python validation helper and the C++ stub.

Outside its scope

  • Sensors and estimation. Sensor noise and estimator dynamics were left out of this first project: the controller is fed the true simulated state.
  • Wheel dynamics. The wheels are torque sources with a limit; their speed and stored momentum are not simulated.
  • Flexibility and changing mass. The body is rigid and its inertia is constant.
  • Detailed environment models. One bounded, constant torque per run stands in for drag, gravity gradient, solar pressure and magnetism.

What this site adds

  • Extension Sensors and estimation: a gyro with bias and noise, a star tracker, and complementary and Kalman-style filters, in module 07 and as clearly marked controls in the simulator.
  • Site option An optional fix for a gap in the mode specification: going back from SAFE_HOLD to SAFE_DETUMBLE if the spacecraft is upset again.
  • Site option Direction-preserving torque scaling as an alternative to per-axis clipping, and actuator delay and quantisation for the architecture module.
  • Site option Forward Euler and deliberately broken RK4 variants, so the integration module can show what goes wrong.
  • Interactive widgets in every module, and the map from 70 subjects to the 13 parts of the project.

How the site reproduces the project

The site's engine re-implements the project's model in JavaScript and runs entirely in your browser: scalar-first quaternions with the Hamilton product, Euler's equation \(J\dot\omega + \omega \times (J\omega) = \tau + \tau_d\), a fixed-step RK4 integrator at 0.01 s Site default with \(q\) renormalised after every step, per-axis clipping of the torque command, and the three-mode safe-mode machine with integer step counters. Its results are checked against reference values from an independent implementation; you can run those engine tests in your browser.

The notes give the control laws but not the gain values, so the PID, detumble and hold gains here are the site's own, and so is the Monte Carlo seed. The sampled trials and the worst case therefore differ from the project's, but both campaigns pass every check:

Evidence labels explained

Every number and every claim on the site says where it comes from. A number tagged Project is stated in the project notes; Derived is computed from those numbers; Site default is a value this site had to choose because the notes do not give one; Site option marks a feature this site offers that the original project did not have, switched off by default unless stated; Illustrative marks example hardware figures; and Extension marks anything beyond the original scope.

Links between subjects and the project carry two more kinds of label. The evidence badge says what the link rests on. For a subject known only from its outline, the site describes the typical content of this subject and never claims what it taught. The strength pill says how much of a part of the project the subject carries: strong for a method the part uses directly, moderate for a supporting idea, weak for background or a brief connection. Analogy marks a link that is a teaching bridge between fields rather than shared content.

Privacy

This site contains no personal information. Subjects are named generically; codes, institutions, people and dates are deliberately omitted.

The project is described only as a student ADCS simulation project, its progress log is numbered by iteration from 1 to 6, and every subject appears only by a generic name and its subject matter. The site sets no cookies and sends nothing anywhere: your theme choice and module ticks stay in your own browser's storage.

Running it yourself

  • Offline: open index.html directly in a browser. There is no build step and no server; all data and libraries are local classic scripts.
  • GitHub Pages: push the folder to a repository and turn Pages on. Every link is relative, so the site works from a project subpath.
  • A local server is optional: python3 -m http.server in the folder, then open the address it prints.
  • Checks: tests/browser.html runs the engine tests in the browser, or run node tests/run-node.js from the folder.
