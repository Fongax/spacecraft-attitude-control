    Dependencies and the critical path

    The work has an order. Requirements come first; the dynamics model needs them; the controllers need the model; the safe-mode logic needs the controllers; verification needs all of it; the report comes last. Three pieces can run in parallel once the controllers exist: the interface and animation, the Python mirror and the C++ stub. The order is a directed acyclic graph, and any topological order of it is a valid schedule, as the Computing Algorithms notes put it.

    The critical path method (CPM) finds the chain of tasks that fixes the finish date. A forward pass gives each task its earliest start and finish; a backward pass from the end gives the latest; the difference is the float, how long a task can slip without moving the end date:

    \[ ES_j=\max_{i\to j}EF_i,\quad EF_j=ES_j+d_j;\qquad LF_i=\min_{i\to j}LS_j,\quad LS_i=LF_i-d_i;\qquad \text{float}_i=LS_i-ES_i \]

    Tasks with zero float are critical. The Algorithms notes add the computer-science view: the critical path is the longest path in a DAG, found in linear time in topological order, even though longest path is NP-hard on general graphs. Durations are uncertain, so PERT replaces each one with an optimistic, most likely and pessimistic estimate:

    \[ t_e=\frac{o+4m+p}{6},\qquad \sigma=\frac{p-o}{6},\qquad \sigma_{path}=\sqrt{\textstyle\sum_{i\in\text{path}}\sigma_i^{2}} \]

    CPM with forward and backward passes, float and PERT estimates are typical content of a project-management subject Typical content. Why does a long chain deserve margin? The Deep Learning and Generative AI notes make the point with chained success: if each step succeeds independently with probability \(p\), all \(n\) succeed with probability \(p^{n}\).

    \[ 0.9^{10}\approx0.35 \]

    Ten tasks that are each 90% likely to finish on time give only a 35% chance that the whole chain does Derived. Two more tools from the notes apply. The Algorithms notes solve the 0/1 knapsack exactly by dynamic programming; applied here, it chooses which optional features fit the time budget. The Intelligent Systems notes pose timetabling as a constraint-satisfaction problem; applied here, scheduling with precedence and resource limits has the same shape.

    FMEA

    A risk register starts from worries. A failure mode and effects analysis starts from parts: for each way a component or function can fail, score how bad the effect is (severity S), how often it is expected (occurrence O) and how unlikely it is to be caught before it matters (detection D), each from 1 to 10:

    \[ \mathrm{RPN}=S\times O\times D,\qquad 1\le\mathrm{RPN}\le1000 \]

    FMEA with this risk priority number is typical content of a mechanical engineering design subject Typical content. Mapped onto the project, likelihood becomes occurrence and impact becomes severity, and the detection score asks a pointed new question: would the verification harness actually catch this? A failure that none of the tests T01 to T06 can see earns a high D however rare it is. The Electromechanics notes suggest the hardware rows a fuller FMEA would add: wheel stall and overheating, Hall-sensor failure, momentum saturation, and closed-loop tuning tests that can oscillate.

    RPN has known weaknesses: the product treats a severity-10 failure that is easy to detect like a severity-2 failure that is not, so a high severity deserves attention whatever the product says.

    Bow-tie: loss of attitude control

    A bow-tie puts one unwanted top event in the middle, here loss of attitude control, with its causes on the left and its consequences on the right. Between them sit two kinds of barrier: preventive barriers that stop a threat from causing the top event, and recovery barriers that stop the top event from turning into a consequence. Bow-tie analysis, risk matrices and fault trees are typical content of a safety-management subject Typical content.

    • Threats: excessive gain, torque saturation, quaternion sign flips, and sensor faults Extension.
    • Preventive barriers: conservative tuning, saturation in every simulation, the shortest-rotation error Project.
    • Recovery barriers: safe-mode entry at 6 deg/s or after a 0.5 s fault, detumble, then hold Project.
    • Consequences: a tumbling spacecraft, a power-negative attitude, lost communications.

    The left side is where the project's design choices live and the right side is where its safe mode lives. A fault tree turns the picture into numbers: for independent events, the top event "a fault occurs and safe-mode entry fails" has probability

    \[ P(A\wedge B)=P(A)\,P(B),\qquad P(A\vee B)=P(A)+P(B)-P(A)\,P(B) \]

    so a recovery barrier that fails one time in a hundred cuts the risk from a fault a hundredfold, as long as its failures are independent of the fault Illustrative.

    The Design of Machine Elements notes describe the same discipline for a design logbook: every decision with its reason, every number with its source, every change recorded as old and new values, and open questions listed.     Scope decisions

    In its first iteration the project saw that its scope "could expand into estimator design" and decided to "keep estimator/noise model out of first project scope" Project. The requirements then said so in an assumption: the true simulated state is used for feedback Project. Declaring an item out of scope prevents scope creep and turns it into a planned extension; on this site that extension is module 07.

    Was that the right call? The Software Engineering and Architecture notes give the test. YAGNI ("you aren't gonna need it") applies to features and abstractions, but not to decisions that are expensive to reverse. Leaving out the estimator is reversible: it can be added later behind the same feedback interface, so deferring it was cheap. The scalar-first quaternion convention, the frame definitions and the units are expensive to reverse, because every equation, file and test depends on them; the project states them once in its notes (scalar-first quaternions, a diagonal inertia in the body frame, SI units with thresholds quoted in degrees) and keeps them fixed everywhere Project.

    The Algorithms notes teach the 0/1 knapsack; applied here, the rest of scope selection is one: each optional feature (the interactive interface, the Python mirror, the C++ stub, the animations) has a value \(v_i\) and an effort \(c_i\), and the budget is fixed:

    \[ \max_{x\in\{0,1\}^n}\ \sum_i v_i x_i\quad\text{subject to}\quad \sum_i c_i x_i\le B \]

    A greedy "best value per hour first" rule can miss the optimum for 0/1 choices; dynamic programming finds it exactly. The Intelligent Systems notes use information gain to choose the next split of a decision tree; applied here, it is a useful tie-breaker: study first the risk or parameter whose answer most reduces uncertainty about the outcome.
