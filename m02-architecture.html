    The closed loop

    An attitude-control system is a feedback loop: measure where the spacecraft points, compare it with where it should point, and push on the difference. The project’s architecture note lists the loop in six steps Project:

    1. A reference attitude qref is supplied as a scalar-first quaternion.
    2. The controller computes a commanded body torque with PID, LQR or detumble rate damping.
    3. The actuator model limits the commanded torque to the reaction-wheel capability.
    4. The rigid-body model propagates the quaternion attitude and the angular velocity.
    5. The state feedback returns the simulated state to the controller.
    6. The safe-mode logic monitors the angular rate and the fault flag, then selects the control mode.

    Steps 1 to 5 are the classic loop of a control course; step 6 sits above it and decides which controller runs. With a controller C(s), a plant G(s) and a feedback path H(s), the closed-loop transfer function from reference to output is

    \[ T(s) = \frac{C(s)\,G(s)}{1 + C(s)\,G(s)\,H(s)} . \]

    Read it as the loop’s promise. Where the loop gain CGH is large, T ≈ 1/H, so the output follows the reference whatever the plant does; where it is small, the plant is on its own. In this project H = 1, because the true state is fed back. Two features keep the spacecraft loop from being a textbook one: the actuator saturates at ±3 mN m, so the loop is linear only for small errors, and the mode manager swaps C(s) at run time, which makes it a switched controller. Transfer functions are used here only as a way of reading the loop; the simulation itself works directly with the nonlinear equations.

    Closed-loop block diagrams, block-diagram reduction and T(s) are typical content of a control systems subject. Drone flight controllers and their failsafes (return to home on link loss or low battery) are typical content of a remotely piloted aircraft systems subject, and they show the same pattern in another vehicle: a feedback loop for the attitude, plus a failsafe mode machine that takes over when something goes wrong.

    Three modes, three controllers

    The project runs three modes, each with its own purpose and its own control law Project:

    Modes and control laws
    ModePurposeController usedTorque law
    NOMINALTrack the target attitude.PID or LQR\(\tau = -K_p q_{e,v} - K_d\,\omega - K_i \textstyle\int q_{e,v}\,dt\)
    SAFE_DETUMBLERemove excessive angular rate.Rate damping\(\tau = -K_d\,\omega\)
    SAFE_HOLDKeep a coarse, stable attitude after detumbling.Low-gain PD hold\(\tau = -K_p q_{e,v} - K_d\,\omega\)

    The important architectural point is what the supervisor does not do. The mode manager never computes a torque. It reads |ω|, the error angle and the fault flag, applies its guards and outputs one thing: which law runs this step. The laws themselves stay simple and separately testable. The sequence is NOMINAL → SAFE_DETUMBLE → SAFE_HOLD → NOMINAL, with hysteresis (enter above 6 deg/s, leave only after 2 s below 0.5 deg/s) and a minimum dwell time of 8 s in SAFE_HOLD, so the modes cannot flap when the rate hovers near a threshold. Two transitions are forbidden outright, SAFE_DETUMBLE → NOMINAL and NOMINAL → SAFE_HOLD, and returning to NOMINAL while the fault is active is forbidden too. Module 08 proves these properties.

    \[ \tau_k = \kappa_{m_k}(q_{e,k},\,\omega_k), \qquad m_k \in \{\mathrm{N},\ \mathrm{SD},\ \mathrm{SH}\} \]

    Several subjects describe the same object in their own language. As a set of modes with an allowed-transition relation it is a directed graph, typical content of a discrete structures subject; with its timers it becomes an extended state machine. As a finite automaton δ(state, input), typical content of a theory of computing subject, filling in the whole δ table forces a decision for every pair. Moore machines built from a state register, next-state logic and counters are typical content of a computer and network architecture subject; in hardware this one needs a 2-bit state register. The object-oriented programming notes teach encapsulation (private and protected members behind getters and setters) and has-a aggregation in class diagrams; applied here, a ModeManager class that keeps its timers private and holds one controller object per mode makes the forbidden transitions impossible by construction. Checklists for each phase of flight, typical content of a flight procedures subject, are the pilot’s version: an ordered sequence of states with explicit entry and exit criteria.

    One time step as a DAG

    On the diagram the loop is a cycle: the controller needs the state, and the state depends on the controller. A program cannot run a cycle, so the simulation breaks it in time. Every step k does the same work in a fixed order:

    \[ \underbrace{x_k}_{\text{read}} \to \underbrace{q_{e,k},\ |\omega_k|}_{\text{errors}} \to \underbrace{m_k}_{\text{mode logic}} \to \underbrace{\tau_{cmd,k}}_{\text{controller}} \to \underbrace{\tau_k}_{\text{saturation}} \to \text{log} \to \underbrace{x_{k+1} = \Phi(x_k, \tau_k)}_{\text{RK4, then renormalise } q} \]

    followed by the integrator update for the PID term. Inside one step the dependencies form a directed acyclic graph (DAG), and the order above is its topological order. The cycle of the physical loop is broken by the one-step delay: the state computed at step k is only read at step k + 1. In a block-diagram tool that delay is the integrator; when it is missing, the tool reports an algebraic loop, which is exactly a cycle inside one step’s graph.

    Order mistakes are quiet. Running the mode logic after the RK4 step, for example, makes it decide on xk+1 while the controller used xk: an off-by-one-step bug that shifts every transition by 0.01 s and pairs the wrong samples in the log. Nothing crashes, and the plots look almost right.

    Each of these ideas starts from something a subject teaches. Computing algorithms notes define directed acyclic graphs and name scheduling and dependency resolution among their uses; applied here, one step’s dataflow is such a graph, and running a node before its inputs are ready is the off-by-one-step bug above. Data structures notes teach topological sort and Kahn’s algorithm, which either produces an order or proves that none exists because the graph has a cycle; here the one-step delay breaks the feedback cycle, and an algebraic loop would be a cycle inside one step’s graph that Kahn’s algorithm reports. Machine-elements notes size a drive in sequence, from transmitted power and speed to gear geometry, tooth forces, shaft loads and bearing loads: the same kind of dependency graph.

    Interfaces and layering

    An interface is a promise between two blocks. The controller’s promise is short: given the error and the rate, return a body torque in N m for each axis. It says nothing about wheels, motors or drivers. As long as every actuator layer accepts “body torque in N m per axis”, the layer can be replaced without changing a line of controller code.

    That is how flight software is tested in stages. In software-in-the-loop (SIL) the controller drives a simulated wheel; in processor-in-the-loop (PIL) it runs on the flight processor against an emulator; in hardware-in-the-loop (HIL) it commands real wheel electronics. Each stage replaces one layer with another that keeps the same contract. What changes is the response: a real driver adds latency, and a digital driver can only command torque in steps (quantisation).

    \[ \tau_k = \mathrm{sat}\big(Q_\Delta(\tau_{cmd,\,k-d})\big), \qquad d = \text{delay in steps}, \quad Q_\Delta(x) = \Delta\,\mathrm{round}(x/\Delta) \]

    Software engineering notes teach dependency inversion (depend on abstractions), the open/closed principle (add a case without editing old code) and the point that composition couples to an interface while inheritance couples to an implementation. Applied here, the controller is a strategy behind an abstract interface, so the loop and the mode manager depend only on the abstraction, and adding a law edits nothing that exists. A spacecraft object has a dynamics model, an actuator, a controller and a mode manager, and swapping the actuator is a composition change, not a new subclass. Networking notes teach that a layer can be replaced by anything that keeps its contract, and the layers above cannot tell; applied here, that is the route from SIL to HIL. Assembly mates in CAD, which constrain how parts may move relative to each other, are a mechanical picture of the same idea and are typical content of a digital design and modelling subject.

    One specification, several programs

    Intelligent Systems notes separate an agent function, the specification of what an agent should do for every history of percepts, from an agent program, the code that implements it. They define an agent as anything that perceives its environment through sensors and acts on it through actuators; drawn as a loop (sensors → program → actuators → environment), that is this module’s block diagram. The notes add a warning that applies here: the state representation caps what the agent can do, because anything not in the state is invisible to every algorithm that runs on it.

    For the attitude controller, the agent function is the set of control laws plus the mode-transition table. Three programs realise it: the MATLAB simulation, the C++ controller stub (for the controller part) and this site’s engine. A fourth, the Python helper, does not realise it at all; it checks the MATLAB outputs.

    Cross-checking programs that implement one function is equivalence testing: run them on the same inputs and compare the outputs. It applies to the three implementations, not to the Python helper, which checks one implementation’s outputs instead of computing its own. Agreement does not prove the specification right, but disagreement proves that at least one program is wrong. It also explains why this site states its own values next to the project’s: where the two differ (for example the integrator clamp described in module 05), the site says so instead of hiding it.

      In short

      The loop is reference → error → controller → saturation → dynamics → feedback, with a mode manager above it that chooses one of three laws but never computes torque. A simulation runs the loop one step at a time in a fixed topological order, and the one-step delay is what turns the physical cycle into a DAG. Because the controller’s contract is “body torque in N m per axis”, the actuator layer can be swapped from simulation to hardware without touching controller code; only the response changes.
